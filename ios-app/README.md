# Lilyshark for iOS

A Capacitor shell around the webapp in `../webapp`. The web bundle inside the
app is byte-for-byte the one lilyshark.com serves; the only addition is
`native-bridge.js`, a Web-Bluetooth-shaped facade over
[@capacitor-community/bluetooth-le](https://github.com/capacitor-community/bluetooth-le)
that is injected ahead of the app bundle. iOS has no Web Bluetooth (WebKit
policy), and that facade fills exactly that hole: the same
`webapp/src/mesh/meshtasticBle.ts` code path that talks to a T-Deck from
Chrome talks to it from an iPhone, with CoreBluetooth underneath instead.

No webapp files were modified. The webapp probes `"bluetooth" in navigator`
at render time and calls `navigator.bluetooth.requestDevice(...)` at connect
time; the bridge defines that property before the app's module bundle runs
(classic scripts execute ahead of deferred module scripts), and only when
running inside the native shell — loading `www/` in an ordinary browser
leaves `navigator` untouched.

## Layout

- `capacitor.config.ts` — points Capacitor at `www/`.
- `src/ble-bridge.ts` — the facade. It implements only the shapes
  `meshtasticBle.ts` uses (`requestDevice`, `gatt.connect`,
  `getPrimaryService`/`getCharacteristic`, characteristic
  read/write/notify) and carries a compile-time assertion that it stays
  assignable to them. Device scans are filtered to the Meshtastic service
  UUID imported from `webapp/src/mesh/meshtasticProto.ts`.
- `scripts/assemble-www.mjs` — copies `webapp/dist` into `www/` and injects
  the bridge `<script>` into the copy, never into `webapp/dist` itself.
- `ios/` — the native Xcode project, generated by `npx cap add ios`
  (Capacitor 8, Swift Package Manager — no CocoaPods). Committed, as is
  normal for Capacitor; `ios/App/App/public` (the copied web assets) is
  gitignored and regenerated by `cap sync`.

## Build

```sh
cd ios-app
npm install
npm run build       # builds ../webapp (its deps must be installed: pnpm install there), assembles www/, bundles the bridge
npx cap sync ios    # copies www/ into the Xcode project and updates plugins
npm run open        # opens ios/App in Xcode
```

`npm run sync` chains build + sync. `npm run typecheck` runs strict tsc over
the bridge.

The webapp uses pnpm (`cd ../webapp && pnpm install`); plain `npm install`
there currently fails on a pre-existing `@shelby-protocol/sdk` /
`@aptos-labs/ts-sdk` peer conflict.

## What is verified vs. scaffold

Verified headlessly on this machine (2026-09-02):

- `npm install` resolves (@capacitor/core+ios+cli 8.5.1,
  @capacitor-community/bluetooth-le 8.3.0).
- `npm run typecheck` passes strict tsc, including the assertion that the
  bridge satisfies the exact `Characteristic`/`BleDevice` shapes in
  `webapp/src/mesh/meshtasticBle.ts`, against the plugin's real installed
  type declarations.
- `npm run build` produces `www/` with `native-bridge.js` injected directly
  ahead of the app's module script in `www/index.html`.
- `npx cap add ios` and `npx cap sync ios` succeed; the plugin is detected
  and written into `ios/App/CapApp-SPM/Package.swift`.
- `NSBluetoothAlwaysUsageDescription` is set in `ios/App/App/Info.plist`
  (iOS terminates the app at first CoreBluetooth use without it) and the
  plist lints with `plutil`.
- An unsigned simulator build compiles: `xcodebuild -project App.xcodeproj
  -scheme App -sdk iphonesimulator CODE_SIGNING_ALLOWED=NO build` ended in
  `BUILD SUCCEEDED`, producing `App.app` with the BluetoothLe plugin linked.

NOT verified — no way to do this headlessly, and nobody has run this on a
phone yet:

- The app has never been launched on an iPhone or simulator. The bridge has
  never moved a real byte over BLE. The mapping plugin-callback →
  `characteristicvaluechanged` → drain loop is faithful to both sides' types
  but is untested against a live T-Deck.
- Signing, provisioning, and anything App Store.

## Human steps left

1. `npx cap open ios`, select the App target → Signing & Capabilities, pick
   your team, and let Xcode create the provisioning profile. The bundle id
   is `com.lilyshark.app` (change it in `capacitor.config.ts` AND Xcode if
   you own a different one).
2. Run on a **physical iPhone**. The iOS simulator has no Bluetooth stack at
   all, so BLE can only be exercised on hardware with a powered T-Deck
   nearby. Expect the Bluetooth permission prompt on first CONNECT, then the
   plugin's native device picker listing decks advertising the Meshtastic
   service.
3. First real-device test: CONNECT → watch for "BLE: configured — N nodes
   known" in the app log, then send a message and check the deck.

## Known caveats before shipping

- **`/api` endpoints do not exist inside the shell.** The page is served
  from `capacitor://localhost`, so relative fetches to `/api/net-nodes` and
  `/api/share/*` (Shelby upload/info) will 404. Mesh-over-BLE, CHAT, NODES,
  MAP tiles (cross-origin, unaffected) work; the Shelby share flow and the
  community-nodes overlay need an absolute API base (e.g. pointing at
  lilyshark.com) before they work on the phone. Deliberately not patched
  here — that is a webapp decision, not a shell one.
- **The service worker is a no-op in the shell.** WKWebView does not run
  service workers for custom schemes; `main.tsx` already guards and
  `.catch`es the registration, so this is harmless — offline capability
  comes from the bundle itself being local.
- **App Store review**: a pure wrapper risks a 4.2 minimum-functionality
  rejection; the native BLE link to a physical radio is the argument that
  this is not just a website. Expect to fill in the privacy questionnaire
  (Bluetooth usage), and `ITSAppUsesNonExemptEncryption` in the Xcode
  project if you want to skip the export-compliance question per build.
- App icon and splash are Capacitor defaults; replace
  `ios/App/App/Assets.xcassets` before shipping.
